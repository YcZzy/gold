# 后台按实际订阅查询行情

## 行为

- 移除全部自选的公共行情预热。黄金和股票都只因已启用、仍在自选且有适用模板授权的提醒进入扫描，再按原有规则时段与每日限额过滤。
- 单纯默认展示黄金、添加自选、增加模板授权，不会自动成为后台查询需求。
- 新账户 `dailyBrief` 默认关闭；迁移仅在旧偏好明确为 true 时开启收盘规则。已经存储的 enabled/true 保留，历史默认与用户主动开启没有足够记录区分，不批量关闭。
- 旧黄金价格/波动监控只请求启用的品种；伦敦金保留所需汇率请求。用户订阅的旧版黄金简报仍含沪金及国际参考，不改变既有消息内容。
- 关闭或删除提醒、授权耗尽后不再为该提醒抓行情。已有待发送任务仍按原有发送前核验处理。
- 定时器继续每分钟执行。股票沿用证券交易日历；后续黄金交易时段修复已接入沪金日夜市及 XAU 参考窗口，休市时不扫描价格提醒，详见 [黄金交易时段](gold-session-filter-2026-11-03.md)。

## 2500 标的的调用量

所有用户的本轮有效需求先去重，最多 2500 标的，通过一次 `marketData/batchQuotes` 调用返回。500 用户各 5 个不同标的是 2500；全部关注相同 5 个标的则只抓 5 个。

内部按最多 30 标的一批，2500 标的是 84 批、最多 10 路并行。这增加行情源请求、数据库访问、数据量和运行时间，不增加跨云函数调用次数。源端回退还可能增加外部 HTTP 请求，不能把 84 批当作固定 HTTP 请求数。超容量明确报错，避免静默遗漏后面的用户。

只计此后台正常调度：每天固定 1440 次 sendTask，加上有有效需求的分钟数次 marketData。若仅 A 股盘中每分钟有需求，约 1680 次/交易日；黄金不再无条件全天查询，仅在其日历允许且有有效需求的分钟增加行情调用；2880 次/日仍是最多每分钟一次批量行情的理论后台上界，不能再直接用作单一黄金品种的日常估算。定时播报和多市场窗口会改变实际活跃分钟数。前台请求、旧版本/重复触发器、失败重试另计，取消预热后前台回源可能增加，因此不保证总量降到 2000。

## 发布

1. 部署整个 sendTask、portfolio、getStatus、savePrefs 目录并安装依赖。
2. 确认 marketData 已部署支持 batchQuotes 的版本；若仍是旧版，一并部署完整目录。沿用现有 60 秒超时建议并检查执行耗时。
3. 更新前端，应用旧提醒页默认关闭及已移除的月额度限制。只改本地文件不会修改正式版。
4. 不清空数据库；cloudCallBudgets 仍供分钟扫描锁使用。已有黄金提醒需要用户自行关闭才能停止对应查询。

本次未上传云函数、发布前端或操作线上用户数据。

## 本地验证

完整 Node 测试 593/593 通过，覆盖无提醒默认自选不查询、无授权不查询、混合自选仅查订阅标的、关闭/删除后停止、500×5 标的一次调用与共享标的去重、新用户默认关闭和已有订阅保留、旧黄金按品种抓取。独立只读复查未发现重要问题；尚无部署后线上耗时或调用量验收。
