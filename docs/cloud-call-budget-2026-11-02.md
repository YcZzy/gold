# 云函数月调用预算优化（2026-11-02）

> 历史方案：2026-11-03 已按用户要求取消新前端的月额度、领取与预扣限制，以下 200 单位与总调用量模型不再适用于当前版本。保留缓存、公共行情及后台扫描优化；更新前端即可生效，无需清空数据。`cloudCallBudgets` 仍用于分钟扫描锁，不可删除。另：2026-11-03 已取消全部自选后台预热，改为按已启用且有授权的提醒查询，下面的“无提醒预热”描述也已失效。当前说明见 README。

## 已确认的问题与修改

此前代码中的放大路径：500个不同股票每分钟分17次调用marketData；详情每分钟分别请求报价、图表及选中的资金/盘口；本地只做失败回退和并发去重。前次100用户、每人800单位的容量模型不适用于本轮500用户：31天按原额度计算可达489,280次。原500个不同标的的扫描上限也无法覆盖500用户各5个不同股票。没有线上逐函数日志，不能断言实际消耗分别来自哪条路径。

本轮用户确认「500用户、每人5股票、分钟级提醒、每人200调用单位」：

1. sendTask每轮把全部需检查的标的合并，最多2500个，统一一次marketData/batchQuotes。内部每30个一批；500个以内最多3批并行，更大集合最多10批并行（2500个为84批，最多9轮），网络请求不再一批一批跨函数调用。单批失败保留其他批成功结果。超过容量明确报错，不静默丢弃尾部用户。普通quotes接口仍最多30个。
2. 交易中的全部自选也参与预热，即使没有提醒、没有通知授权，也可更新前台公共报价；这不创建任务或扣通知授权。休市沿用快照，提醒筛选与模板余量逻辑保留。
3. 行情服务写入专用publicQuotes，每个文档仅证券资料、标准化行情和更新时间。前台按20个一组直接读这个集合；报价两分钟内或非交易时段可复用。过期、数据源延迟和失败回退保留sourceTime并标记缓存/延迟；未来时间、身份错配、不可用和超过7天的报价不使用。客户端时段判断为保守交易窗口，不包含节假日日历，节假日交易窗口可能回源，但受额度约束。
4. 前台所有wx.cloud.callFunction在app初始化后共用额度入口：北京时间自然月每用户200调用单位，包含嵌套调用及领取额度本身。callBudget函数使用cloudCallBudgets事务，每次分配100单位（99供业务调用，1支付领取调用），同账号多设备累计不超过200个新分配单位。清缓存会丢失未用余额，不能重新领取整个月额度。服务端只信任真实OPENID，不接受客户端身份、月份或领取金额。此前当月已分配超过200的账户直接返回额度耗尽，保留原账本；不能撤销已发出的旧额度或已发生计费。
5. 前台对portfolio预扣61、ledger预扣32的嵌套上界，其余函数1；portfolio/ledger响应返回服务端实际调用数，成功收到响应后退差额。超时不退，避免已在服务端执行却被当作未计费。本地额度扣减无法持久化时，在网络请求前阻止调用；已成功的业务操作不会因退额持久化失败被误报失败。领取不足只禁止继续领取，不阻止花费已有的小额余额。失败、未部署、额度服务中断时阻止业务请求，保留现有数据/草稿。额度服务暂时失败冷却5分钟，月额度耗尽后本月不反复领取。
6. 图表成功结果本设备复用15分钟；证券资料24小时、搜索及市场发现5分钟。相同只读请求在额度入口合并，写操作独立发送，授权状态不做TTL。手动刷新同样遵守额度和TTL，不能通过连续点击绕过。命中正常图表缓存显示缓存提示，不冒充刷新失败。
7. Type=Timer的dispatchTimer及旧scanTimer通过单个事务文档按分钟竞争扫描权。重复触发仍可分发已有任务，但不会同分钟再次扫行情。重复触发器自身仍会计费，上线必须删除额外触发器。

## 31天容量模型

| 项目 | 最坏正常调度模型 |
| --- | ---: |
| 每分钟一次sendTask定时调用 | 44,640 |
| 每分钟最多一次marketData批量调用 | 44,640 |
| 500用户×200调用单位（含成功领取及嵌套） | 100,000 |
| 合计 | **189,280** |
| 距200,000剩余 | **10,720** |

A股22交易日、每天240交易分钟时，后台行情实际仅约5,280次。2500个不同股票若继续每30个跨函数分批，一轮84次、每月约443,520次；合并为单次后这条调用路径减少约98.8%。此为相同2500股票模型，不含播报额外窗口。不同市场重叠、黄金全天可用时按上表每分钟一批上界估算。

200是调用单位而非200次用户操作；每人最多两次成功领取，最多198个业务单位，部分操作包含多层调用。预扣需要足够可用余额，接近上限时可能提前拒绝高成本操作。后台分钟提醒和已有公共报价查看不依赖该客户端操作额度。

该数字是**正常新版本工作负载预算，不是云平台绝对计费硬上限**：旧版本、旧800额度在本月已发出的余额、额外触发器、手动云端运行、未受前台入口约束的直接调用、超时/失败/被拒绝的领取、部署测试和超出500用户都会额外计费。函数内部拒绝也算一次调用，代码无法撤销这笔计费。未查询线上用量、未验证平台级硬配额能力；应配合云平台预算告警/可用的额度策略，并按函数明细核对实际部署后增量。

本轮转移了部分费用到数据库：前台读取publicQuotes、后台更新投影/证券资料、事务额度分配和扫描锁均有独立数据库消耗，不承诺整体账单同比例下降。公开数据源无稳定SLA，2500个标的慢源/大量回退、元数据冷启动或数据库耗时可能超过扫描预算时间；必须在云端核验执行时长和并发，不能承诺严格60秒送达。提高到10批并行只是限制并发并减少等待轮数，本地模拟不代表线上压测。

## 部署顺序（尚未执行生产部署）

1. 先部署并运行整个initDb，幂等创建 **publicQuotes、cloudCallBudgets**，不清空旧数据。
2. 按docs/database-permissions.json设置：只有publicQuotes允许客户端读、禁止客户端写；cloudCallBudgets及所有原有私密集合继续禁止客户端读写。不要直接开放quoteCache、instruments或portfolios。
3. 部署新增 **callBudget**，以及完整 **marketData、portfolio、ledger、sendTask**（含batch-quotes.js、scan-lease.js等同目录依赖），选择云端安装依赖。先完成服务端再更新前端，避免额度函数缺失导致操作被拦截。
4. sendTask仅保留config.json里的一个每分钟dispatchTimer，删除云端残留scanTimer/重复触发器。原函数3秒默认超时不适用于2500标的：sendTask及marketData先配置60秒并监控耗时，先预热证券资料，再在2500不同标的交易窗口检查耗时/超时/重叠；若无法在预算时间内完成，需继续优化数据源或批处理，不能视为已满足分钟时效。callBudget等轻量函数沿用现有合理超时。
5. 上传体验版/正式发布新小程序（含app.js和新增utils模块）。仅部署云函数不会更新用户设备的前台读取和月额度控制。旧版本流量需要观察，不能用新模型覆盖未升级的旧版本。
6. 在有2500个不同股票的交易窗口检查：单次sendTask只跟随1次batchQuotes；scanStats.marketCalls=1，quotedAssets≤2500；publicQuotes持续更新；前台连续看盘的报价读不出现quote/quotes函数调用。首次证券资料、图表、搜索和缺失快照回源仍可能调用。
7. 验证同账号两设备共用分配额度、预算不足写操作不提交/草稿保留、通知授权仍按原账本扣减。检查sourceTime与缓存标记。部署后观察1小时的函数增量及执行时长；已消耗的本周期累计次数不会回退。
